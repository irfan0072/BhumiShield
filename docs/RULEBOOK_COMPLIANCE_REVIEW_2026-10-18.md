## Verdict

**Strong topic fit; full compliance cannot be certified. README needs correction before submission.** The most serious conflict is the government-page collector. The supplied rules prohibit scraping government websites, including public pages; the restriction is not limited to bulk collection or private land records. Earlier implementation proceeded without this rulebook being checked. That was a mistake. The known collector worker started in this chat was stopped during this review (session ended with exit 130). The collection code and manual collection endpoint still exist; stopping this worker is not a permanent application-level disablement and does not undo earlier collection. No records or history were erased.

The current project should be described as a **working prototype**, not a nationally deployed, government-approved, fully secure service. Round 1 explicitly accepts a working prototype (PDF p9/p14). Existing software defects are relevant to accuracy of claims and demo readiness, but they do not automatically disqualify a prototype under a production-completeness requirement that the rulebook does not impose.

## Exact README corrections

1. **Lines 296–300 — data disclosure:** “100% synthetic” must be limited to verified business demo fixtures, not every asset or collected public text. The “zero scraping” heading and denial conflict with the collector and its implementation log. State actual collection history honestly; describe the competition build's fixture-only mode only after it is implemented and verified. Removing observations does not erase the historical conflict. Seek organizer assessment; do not assert eligibility restored.
2. **Lines 60–68 — primary problem:** explicitly name one P code. P3 is a recommendation based on the current rule engine, not proof of the registered selection. Present other modules as support, not five independently completed submissions.
3. **Lines 201–235 — reproducible setup:** use the verified Node version, explain custom local autoload/bootstrap instead of assuming Laravel conventions, document environment/provider settings, API endpoint configuration and PHP extensions. The checked-in `backend/vendor/autoload.php` is a small custom loader; there is no `backend/composer.lock`. Do not blindly add a Composer install step without proving a fresh checkout works. Test README steps in a disposable checkout/database. Label `migrate:fresh --seed` as destructive and demo-only; never recommend it on an existing service database. Explain isolated tests and demo credentials clearly.
4. **Line 207 — database support:** `backend/app/Support/DB.php` accepts SQLite/PostgreSQL and rejects unsupported drivers. Remove MySQL support unless implemented and tested. PostgreSQL support exists in code; do not imply it passed integration/load tests without evidence.
5. **Lines 8, 308–309 — stack/credits:** `frontend/package.json` declares React **19.3.1**, Leaflet **1.9.4**, Vite **6.4.4**, Tailwind **4.3.3**. README claims React 18 and MapLibre/Canvas Confetti. List actual direct dependencies and credits, including Leaflet/OpenStreetMap attribution for the displayed basemap. CSS font tokens include Manrope, Hind Siliguri and Noto Sans Bengali; verify loaded fonts before listing legacy fonts.
6. **Lines 7, 240–251 — tests:** the existing audit recorded 128 standard-runner checks plus separate suites, 280 total. Do not silently replace the badge with a fresh 280-pass claim: this review did not rerun those gates and three audited source files changed. The standard runner does **not** include `LawyerPortalTest`, despite README implying otherwise. State command, scope, date/source state and limitations. Passing tests are not proof of zero vulnerabilities.
7. **Line 12 — accessibility:** WCAG 2.1 AA conformance is not established by the available checks. Say “Bangla-first; accessibility review pending” or report an actual accessibility audit with method and scope.
8. **Lines 18–20, 181–197 and associated feature copy — security/legal claims:** replace “immutable”, “impossible even through direct SQL”, “constitutional guard”, “fraud-free/clear-title guarantee” with precise prototype properties and threat boundaries. Hashes/signatures can detect certain changes; privileged key/database administrators remain part of the threat model. Application signing is not an official government signature or title opinion. AC Land mutation authorization is the prototype's configured workflow rule, not proof of a universal legal proposition.
9. **Lines 78, 99, 177, 281, and demo script — external providers:** authorized-lawyer table lookup is not a live Bangladesh Bar Council check. Biometric/NID/payment simulations and provider interfaces are not operational fingerprint, face-liveness, EC/NID, bank or government gateway integration. Disclose simulation and unavailable integrations explicitly.
10. **Lines 82, 134 — GIS:** drawing/allocating a proposed parcel is not proof of legal subdivision/merge, full survey operations or an authoritative national cadastre. Say precisely what can be drawn, reviewed and assigned. Reference centers/OSM tiles are not official cadastral boundaries.
11. **Lines 287–290 — all-role completeness:** replace blanket “complete end-to-end workflows” with tested scope. Existing critical transfer issues remain in unchanged code, including wrong-buyer fallback, consent bypass and premature PAID DCR projections. Government-looking output must be visibly a sample, and must not imply payment/order issuance that did not occur.
12. **Lines 302–305 — AI disclosure:** list actual Antigravity, OpenAI ChatGPT/Codex, Anthropic Claude use with accurate tasks. Do not label AI legal suggestions “verified law.” Only name exact models/providers if confirmed. Keep student responsibility explicit.
13. **Lines 313–328 — demo:** prominently distinguish Round 1 video ≤3 minutes from final pitch/live demo five minutes plus three-minute Q&A. Do not hardcode “1420 blocks” or rely on demo records that may not exist. Use stable synthetic scenarios and show honest expected results.
14. Add concise **current limitations**, selected problem, source/data provenance, countrywide rollout plan and dated change history. Team/mentor details are mandatory in the concept note; adding a concise team table to README is helpful but not separately mandated there.

All checked local Markdown links/images in README resolve. This checks file existence, not screenshot freshness, content accuracy, accessibility or external URL availability.

## Recommended concept-note framing

Subject to the team's actual registered problem: **P3 — Catch Fraud & Double-Selling**.

Title: **BhumiShield: Explainable Fraud Checks Across Land Registration and Mutation**.

Core story: one synthetic parcel, one recorded ownership chain, explainable risk checks before a proposed transfer; registration and mutation actors share traceable workflow state; citizen sees understandable status. SHA-256/Ed25519 provide application-level integrity evidence. Supporting maps and service guidance help users locate context; they do not replace authoritative surveys, adjudication or government systems.

Four-page plan: (1) problem/users/value; (2) workflow/architecture/stack; (3) features/evidence/limits and data ethics; (4) phased Bangladesh rollout, evaluation plan, team and mentors, short references. This is an editorial recommendation. The rulebook does not mandate page order, font, margins, English, a cover page or a word count.

Before upload: resolve the collection conflict with organizers, verify allowed data in the submission, correct README, supply real team metadata, verify repository access, export and visually inspect ≤4 PDF pages, and verify the actual demo video duration. No document-writing prompt can substitute for these actions.
